# Розподілені інформаційні системи. Практичне завдання 5: реплікація з одним і з кількома лідерами

*Виконав: Вяльцев Олександр*

[GitHub — код лабораторної роботи](https://github.com/VialtsevOleksandr/Big-Data-and-DIS-Labs/tree/main/Lab5_Replication)

Реалізовано сервіс нотаток на PostgreSQL 18.1 у двох конфігураціях. Конфігурація A —
лідер і два фоловери з вбудованою потоковою фізичною реплікацією. Конфігурація B —
два лідери з вбудованою логічною реплікацією в обидва боки. Кожен вузол працює
в окремому контейнері Docker, обидві конфігурації запускаються через Docker Compose.

Нотатка має ідентифікатор, автора, заголовок, текст і час останньої зміни.
Сервіс уміє створити нотатку, змінити її заголовок або текст, видалити її,
прочитати за ідентифікатором і повернути список нотаток автора.
Тестовий застосунок написано на Python 3.12 з бібліотекою psycopg 3.

Схема даних — одна таблиця:

```sql
CREATE TABLE notes (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    author_id  integer     NOT NULL,
    title      text        NOT NULL,
    body       text        NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT clock_timestamp()
);
CREATE INDEX notes_author_updated_idx ON notes (author_id, updated_at DESC);
```

Генератор детермінований: той самий seed дає той самий набір. Поруч із файлом
даних він записує маніфест із параметрами й SHA-256 набору, а перед завантаженням
перевіряє, що файл не змінився.

Тестовий застосунок пише на лідера, читає з фоловерів і веде власний журнал
`journal.csv`. На кожну спробу запису журнал містить порядковий номер, результат,
ідентифікатор, який повернула база, унікальний заголовок `<запуск>/<номер>`, вузол,
що підтвердив запис, і час підтвердження. Звірка шукає кожен підтверджений запис
на кожному вузлі за парою «заголовок + ідентифікатор». Кількість нотаток і
контрольна сума вузла — це `count(*)` і MD5 від MD5 усіх рядків, упорядкованих за `id`.

## Налаштування реплікації

### Конфігурація A — потокова фізична реплікація

Лідер `pg1` створюється звичайним `initdb` зі схемою і ролями. Фоловери стартують
із порожнім томом. Спеціальна точка входу [node-entrypoint.sh](config/scripts/node-entrypoint.sh)
клонує лідера через `pg_basebackup` і записує, за ким іде вузол. Після цього вузол
запускається з файлом `standby.signal`, тобто в режимі постійного відновлення.

| Параметр | Значення | Призначення |
| --- | --- | --- |
| `wal_level` | `replica` | У WAL є все потрібне для фізичної копії вузла |
| `max_wal_senders` | 10 | Процеси, що передають WAL фоловерам і `pg_basebackup` |
| `max_replication_slots` | 10 | Слоти, що змушують лідера зберігати WAL для фоловера |
| `wal_keep_size` | 0 | WAL утримують лише слоти |
| `max_slot_wal_keep_size` | -1, у досліді межі — 32MB | Межа WAL, яку слот може втримати |
| `synchronous_standby_names` | порожньо, в експерименті 2 — `FIRST 1 (pg2)` | Синхронний фоловер |
| `synchronous_commit` | `on` | `COMMIT` чекає скидання WAL на диск (і синхронного фоловера, якщо він заданий) |
| `wal_log_hints` | `on` | Потрібен для `pg_rewind` |
| `hot_standby` | `on` | Читання з фоловера |
| `wal_sender_timeout`, `wal_receiver_timeout` | 10s | Через скільки тиші з'єднання вважається втраченим |
| `wal_receiver_status_interval` | 1s | Як часто фоловер звітує про позиції WAL |
| `wal_retrieve_retry_interval` | 2s | Пауза між спробами фоловера під'єднатися знову |
| `recovery_min_apply_delay` | 0, в експерименті 1 — 1s | Штучна затримка відтворення |
| `primary_conninfo` | `host=<лідер> user=replicator application_name=<вузол>` | Звідки фоловер бере WAL |
| `primary_slot_name` | `pg2_slot`, `pg3_slot`, `pg1_slot` | Слот фоловера на лідері |

Кожен вузол має дві мережі. Мережа `repa-repl` з'єднує лише вузли СУБД, і саме її
розриває `docker network disconnect`. Кожен вузол має ще й окрему клієнтську мережу
з застосунком. Тому під час розриву вузол працює й доступний застосунку,
але інших вузлів не бачить.

Роль `replicator` має атрибут `REPLICATION`. Для неї в `pg_hba.conf` додано окремий
рядок `host replication`, бо ключове слово `all` у полі бази не охоплює з'єднань
фізичної реплікації. Файл `pg_hba.conf` лежить у каталозі даних, тому `pg_basebackup`
переносить його на фоловери разом із даними.

### Конфігурація B — логічна реплікація в обидва боки

Обидва лідери створюються однаково: `initdb`, схема, ролі й публікація
`CREATE PUBLICATION notes_pub FOR TABLE notes`. Після старту кожен вузол підписується
на інший:

```sql
CREATE SUBSCRIPTION sub_pg1_from_pg2
    CONNECTION 'host=repb-pg2 dbname=notes user=replicator ...'
    PUBLICATION notes_pub
    WITH (copy_data = false, origin = none);
```

| Параметр | Значення | Призначення |
| --- | --- | --- |
| `wal_level` | `logical` | WAL можна декодувати в зміни рядків |
| `track_commit_timestamp` | `on` | Час кожного коміту; з ним PostgreSQL розпізнає зміну рядка іншим вузлом |
| `max_logical_replication_workers` | 4 | Процеси застосування змін на підписнику |
| `copy_data` | `false` | Обидва вузли стартують порожніми, початкова копія не потрібна |
| `origin` | `none` | Підписник отримує лише зміни, що виникли на самому видавці, тож зміна не ходить по колу |
| Послідовність `id` | `INCREMENT BY 2`: pg1 — непарні, pg2 — парні | Логічна реплікація не передає стан послідовностей |

### Проблеми і як їх подолано

1. Образ PostgreSQL 18 тримає каталог даних у `/var/lib/postgresql/18/docker`.
   Том змонтовано в `/var/lib/postgresql`. Налаштування вузла (`primary_conninfo`,
   `primary_slot_name`) записуються у файл `node.conf` поза каталогом даних і
   підключаються з `postgresql.conf` через `include_if_exists`. Через це їх не
   перезаписують ні `pg_basebackup`, ні `pg_rewind`, а спільний `postgresql.conf`
   однаковий на всіх вузлах, хоч ролі після failover і змінюються.
2. Щоб лідер не видалив WAL, потрібний новому фоловеру, слот створюється ще до початку
   копіювання (`pg_basebackup --create-slot`).
3. Після failover фоловер `pg3` переходить на нового лідера без перезапуску:
   новий `primary_conninfo` і `pg_reload_conf()`. На новому лідері заздалегідь
   створюються слоти для решти вузлів.
4. Windows PowerShell 5.1 перетворював на помилку будь-який рядок, який Docker пише
   в stderr, зокрема прогрес завантаження образу. Скрипти перевіряють лише код
   виходу команди, а stderr друкують як звичайний вивід.
5. На одній машині фоловер після відновлення мережі наздоганяє лідера за частки
   секунди. Вимір наздоганяння запускається ще до відновлення зв'язку: він фіксує
   позицію WAL лідера і кожні 10 мс опитує фоловер.
6. Лідер раз на кілька хвилин зупиняється приблизно на 1–1,5 с, скидаючи на диск
   контрольну точку. Навантаження надолужує пропущені моменти запису, якщо відстає
   не більше ніж на 5 с, тому середній темп лишається рівно заданим.
7. У конфігурації B зміна, отримана з іншого вузла, без `origin = none` повернулася б
   назад на свій вузол. Послідовності в логічну реплікацію не входять, тому кожен
   вузол налаштовується окремо.

## Експеримент 1 — відставання реплікації і читання власних записів

Реплікація асинхронна. Застосунок записує нотатку на `pg1` і одразу читає її за
`id` з `pg2` — по 10 000 разів у кожній фазі. Паралельно кожні 200 мс знімається
відставання засобами СУБД: на лідері — `pg_stat_replication` (`replay_lag`,
різниця `pg_current_wal_lsn()` і `replay_lsn`), на фоловері —
`pg_last_wal_receive_lsn()`, `pg_last_wal_replay_lsn()` і
`pg_last_xact_replay_timestamp()`.

Штучна затримка вмикається на фоловері засобами СУБД:

```sql
ALTER SYSTEM SET recovery_min_apply_delay = '1s';
SELECT pg_reload_conf();
```

| Фаза | Затримка відтворення | Читання | Читань | Застарілих | Застарілих, % | `replay_lag` p50, мс | `replay_lag` p99, мс |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 0 | з фоловера | 10 000 | 9 998 | 99,980 | 2,292 | 68,345 |
| 2 | 0 | read-after-write | 10 000 | 0 | 0,000 | 2,665 | 14,728 |
| 3 | 1 с | з фоловера | 10 000 | 10 000 | 100,000 | 995,893 | 1 000,621 |
| 4 | 1 с | read-after-write | 10 000 | 0 | 0,000 | 995,987 | 1 010,952 |

Для 30 застарілих читань окремо виміряно, через скільки запис з'являється на
фоловері: без затримки — медіана 5,587 мс, із затримкою — 998,778 мс.

Read-after-write реалізовано через позицію в журналі. Після кожного запису сесія
запам'ятовує `pg_current_wal_flush_lsn()` лідера. Перед читанням вона перевіряє на
фоловері `pg_last_wal_replay_lsn() >= <позиція>`. Якщо фоловер уже відтворив запис,

## Відповіді на питання до звіту

1. Яку СУБД і який механізм реплікації ви обрали для кожної конфігурації і чому? Що саме лідер передає фоловерам: SQL-інструкції, фізичний журнал (WAL), логічний журнал змін рядків, щось інше? Як ви це перевірили?

Для обох конфігурацій обрано PostgreSQL 18.1 і лише вбудовані механізми реплікації,
без розширень і зовнішніх інструментів. У конфігурації A використано потокову
фізичну реплікацію: це стандартний спосіб PostgreSQL мати лідера з фоловерами,
вона копіює весь кластер байт у байт і має повний набір засобів для досліду —
слоти, `pg_basebackup`, синхронний режим, `pg_promote()` і `pg_rewind`.

У конфігурації B використано логічну реплікацію, налаштовану в обидва боки:
кожен вузол публікує свою таблицю і підписується на таблицю іншого. Фізична
реплікація для двох лідерів не підходить, бо фоловер у ній працює лише на читання.
PostgreSQL 18 записує в журнал і рахує в `pg_stat_subscription_stats` кожен вид
конфлікту, тому результат кожного випадку експерименту 5 видно напряму.

У конфігурації A лідер передає фізичний журнал WAL — зміни сторінок даних.
Ознаки: усі три вузли мають однаковий `system_identifier` 7709674644654743593, тобто
це копії одного кластера, а не окремі бази. Позиції реплікації в
`pg_stat_replication` — це байтові позиції WAL (`sent_lsn`, `replay_lsn`), і відставання
в експерименті 1 вимірюється в байтах журналу. Схему і ролі фоловери отримали разом
із файлами, без жодного SQL, а послідовність `id` після failover продовжилася на
новому лідері без конфліктів.

У конфігурації B передається логічний журнал змін рядків: плагін `pgoutput` декодує
WAL видавця в операції `INSERT`, `UPDATE` і `DELETE` зі значеннями стовпців. Журнал
підписника показує саме рядок, а не текст запиту:
`Remote row (4003, 1, ..., body changed on pg2 ...); replica identity (id)=(4003)`.
Якби передавалися SQL-інструкції, `INSERT` без `id` отримав би на іншому вузлі новий
`id` зі своєї послідовності. Насправді `pg2` отримав рядок із готовим `id = 4005` і
зупинився на конфлікті первинного ключа. Таблицю на обох вузлах довелося створити
окремо, а послідовності налаштувати на кожному вузлі окремо, бо DDL і стан
послідовностей логічна реплікація не передає.

2. Як ви підключили другий фоловер до лідера, що вже працював і приймав записи? Звідки фоловер узяв початкову копію даних і як він дізнався, з якого місця журналу продовжувати?

У момент підключення лідер мав 151 208 нотаток і приймав 100 записів на секунду.
Контейнер `pg3` стартував із порожнім томом, і його точка входу запустила
`pg_basebackup --wal-method=stream --create-slot --slot=pg3_slot --checkpoint=fast`
з лідера. Від старту контейнера до стану `streaming` минуло 20,141 с. За цей час
лідер підтвердив 2 014 записів без жодної помилки. Після зупинки навантаження всі
три вузли мали 153 782 нотатки з однаковою контрольною сумою.

Початкову копію `pg3` узяв прямо з лідера через протокол реплікації: `pg_basebackup`
скопіював файли кластера, поки лідер працював. Файли, скопійовані в різні моменти,
між собою не узгоджені, тому паралельно друге з'єднання забирало весь WAL, записаний
лідером під час копіювання, — від `0/C000210` до `0/C26E850`. Слот `pg3_slot` створено
ще до початку копіювання, тож лідер не міг видалити цей WAL.

Позицію старту `pg_basebackup` записав у файл `backup_label` усередині копії:
`START WAL LOCATION: 0/C000210`. Запустившись, `pg3` почав відтворення саме з цієї
позиції (`redo starts at 0/C000210`), досяг узгодженого стану на кінці копії
(`consistent recovery state reached at 0/C26E850`) і далі запросив у лідера потік
через той самий слот: `START_REPLICATION SLOT "pg3_slot" 0/D000000`. Адресу лідера
і назву слота фоловер бере з `primary_conninfo` і `primary_slot_name`.

3. Яке відставання ви виміряли і яка частка читань з фоловера була застарілою — без штучної затримки і з нею? Який спосіб отримати read-after-write ви реалізували і чого він коштує: які запити тепер ідуть на лідера або чекають?

Без штучної затримки `pg_stat_replication.replay_lag` мав медіану 2,292 мс і 99-й
перцентиль 68,345 мс. Тобто фоловер відстає на одиниці мілісекунд: після підтвердження
на лідері він має отримати WAL, скинути його на диск і відтворити. Застосунок читає
одразу після підтвердження, у середньому через 0,687 мс, тому не побачили щойно
зроблений запис 9 998 читань із 10 000 — 99,980%. Запис з'являвся на фоловері в
середньому через 5,587 мс після підтвердження.

Із затримкою `recovery_min_apply_delay = 1s` медіана `replay_lag` — 995,893 мс,
99-й перцентиль — 1 000,621 мс, а застарілими були всі 10 000 читань. Запис ставав
видимим на фоловері в середньому через 998,778 мс. Різниця між поточною позицією WAL
лідера і позицією відтворення фоловера мала медіану близько 0,099 МіБ.

Read-after-write реалізовано через позицію в журналі. Після кожного запису сесія
користувача запам'ятовує позицію WAL лідера, до якої цей запис уже скинуто на диск.
Перед читанням вона перевіряє, чи фоловер відтворив журнал до цієї позиції. Якщо так —
читає з фоловера. Якщо ні — чекає до 10 мс, перевіряючи щомілісекунди, а потім
читає з лідера. В обох фазах із read-after-write застарілих читань — 0.

Ціна така. Після кожного запису — додатковий запит до лідера, щоб узяти позицію.
Перед кожним читанням — додатковий запит до фоловера. Без затримки 9 963 читання
з 10 000 чекали на фоловер (медіана 2,872 мс), 35 пішли на лідера, а медіана читання
зросла з 0,687 до 3,656 мс. Із затримкою 1 с жодне очікування не вкладалося в 10 мс,
тож усі 10 000 читань пішли на лідера і кожне ще й чекало 10 мс: медіана читання —
12,113 мс. Тобто за великого відставання власні нотатки читаються з лідера, і його
навантаження зростає. Читання чужих нотаток цієї перевірки не потребує і лишається
на фоловерах.

4. Наскільки синхронний режим сповільнив записи на ваших вимірах? Що сталося із записами, коли синхронний фоловер зник, і як довго це тривало? Який режим ви обрали б для сервісу нотаток і чим готові за це заплатити?

Медіани трьох запусків: в асинхронному режимі p50 — 4,716 мс, p95 — 6,404 мс,
p99 — 8,917 мс; із синхронним `pg2` — 5,747 мс, 8,073 мс і 9,876 мс. Синхронний режим
додав приблизно 1 мс до кожного запису: p50 зріс на 21,9%, p95 — на 26,1%, p99 —
на 10,8%. Пропускна здатність одного з'єднання впала приблизно з 194 до 165 записів
на секунду. На одній машині мережа майже нічого не коштує, тож ця 1 мс — здебільшого
очікування скидання WAL на диск фоловера. Між окремими серверами до неї додався б
мережевий обмін.

Коли синхронний фоловер зник, лідер продовжив записувати транзакції у свій WAL,
але не повертав `COMMIT` клієнту: транзакція чекала підтвердження від `pg2`.
Через 31,726 с запит застосунку на лідері стояв у стані `active` з
`wait_event = SyncRep`. Застосунок не отримав жодної помилки — просто чекав.
Підтвердження не було 68,084 с, хоча розрив тривав 65,115 с: решта — час, поки `pg2`
знову під'єднався. Запис завершився сам через 0,011 с після того, як лідер знову
оголосив `pg2` синхронним фоловером.

Посеред розриву `pg1` і `pg2` показували 256 931 нотатку, а асинхронний `pg3` — 256 932.
Тобто запис, який лідер ще не підтвердив і не показував іншим сесіям, уже був
видимий на асинхронному фоловері. Жодного підтвердженого запису не втрачено.

Для сервісу нотаток я обрав би `synchronous_standby_names = 'ANY 1 (pg2, pg3)'`:
кожен запис підтверджує хоча б один із двох фоловерів. Ціна — приблизно 1 мс на
запис, як у вимірі. Натомість після відмови лідера підтверджений запис гарантовано
є щонайменше на одному фоловері, а зникнення одного фоловера не зупиняє записи,
як `FIRST 1 (pg2)` у нашому досліді. Записи зупиняться лише тоді, коли недоступні
обидва фоловери.

5. Які результати розривів на 5, 10 і 15 хвилин? Як час наздоганяння залежить від тривалості розриву? За якого обмеження журналу фоловер уже не зміг наздогнати лідера і як ви його відновили? Що відбувається з диском лідера, поки фоловер недоступний, якщо журнал не обмежувати?

Результати наведено в таблицях експерименту 3. За розриви на 5, 10 і 15 хвилин лідер
підтвердив 30 392, 60 444 і 90 474 записи, а `pg2` перед відновленням відставав на
30 351, 60 407 і 90 437 нотаток. В усіх трьох дослідах фоловер наздогнав лідера сам,
без жодних дій: за 3,041 с, 3,075 с і 0,612 с від відновлення мережі. Після цього
кількість нотаток і контрольні суми на `pg1` і `pg2` збіглися, а звірка з журналом
застосунку не знайшла жодного відсутнього запису.

Час наздоганяння складається з двох частин. Перша — поки фоловер знову під'єднається:
від 0,282 до 2,869 с. Вона не залежить від тривалості розриву. Фоловер повторює
спроби під'єднання приблизно кожні 4 с, і результат залежить від того, в яку фазу
цього циклу потрапило відновлення мережі. Друга — саме відтворення накопиченого WAL:
0,172 с, 0,269 с і 0,330 с, зі швидкістю 180–400 МіБ/с. Вона зростає з обсягом
накопиченого WAL, а не прямо з тривалістю розриву.

Обсяг WAL не пропорційний кількості записів: 68,348 МіБ за 5 хвилин, але 49,289 МіБ
за 10 хвилин. WAL пишуть не лише записи застосунку. Після кожної контрольної точки
перша зміна сторінки записує в журнал її повну копію, і їх кількість залежить від того,
скільки контрольних точок і які сторінки припали на розрив. Фонові процеси, зокрема
autovacuum, теж пишуть у WAL. На одній машині відтворення таких обсягів займає частки секунди.
Між серверами різниця була б помітнішою, бо WAL ще треба передати мережею.

Із `max_slot_wal_keep_size = 32MB` і навантаженням 200 записів на секунду по 2 500
байтів слот `pg2` вийшов за межу приблизно через 20 с розриву (37,918 МіБ). На найближчій
контрольній точці лідер видалив потрібні сегменти і оголосив слот втраченим
(`wal_status = lost`, причина `wal_removed`). Після відновлення мережі `pg2`
19 разів поспіль отримав `can no longer access replication slot "pg2_slot"` і за 30 с
не отримав жодного запису. Наздогнати лідера він уже не міг: потрібних сегментів
немає ні на лідері, ні в архіві. Фоловер відновлено новою повною копією — видалено
його том і знову запущено контейнер, точка входу якого виконала `pg_basebackup`.
Від старту контейнера до потокової реплікації минуло 6,750 с, після чого обидва вузли
мали 460 035 нотаток з однаковою контрольною сумою.

Якщо журнал не обмежувати, слот недоступного фоловера утримує на лідері весь WAL,
записаний із моменту розриву. Під навантаженням 100 записів на секунду це було
81,917 МіБ за 904,648 с — близько 0,091 МіБ/с, або приблизно 326 МіБ на годину
і 7,6 ГіБ на добу. У наших дослідах каталог `pg_wal` лишався 176 МіБ, бо утримані
сегменти вміщалися в уже виділені й повторно використовувані файли. Але якщо фоловер
не повернеться, `pg_wal` ростиме, доки не закінчиться місце на диску, і тоді лідер
зупиниться і перестане приймати записи. Один забутий фоловер може зупинити весь сервіс.

6. Скільки підтверджених записів ви втратили під час failover і чому саме стільки? Як застосунок дізнався про нового лідера? Що сталося зі старим лідером після повернення і що у вашій конфігурації заважає (або не заважає) двом вузлам одночасно вважати себе лідером (split brain)?

Під час failover не втрачено жодного підтвердженого запису. Старий лідер підтвердив
3 164 записи, і всі вони є на `pg2` і `pg3`. Один запис, надісланий `pg1` у момент
`docker kill`, не отримав підтвердження і не потрапив на жоден вузол — застосунок
бачив помилку. Записи не втрачено, бо асинхронні фоловери встигли отримати весь WAL
старого лідера. Обидва мали отриману позицію `0/14882490`, а сам `pg1` після перезапуску
показав `redo done at 0/14882468` — це останній його запис. Фоловер відстає на одиниці
мілісекунд, а між останнім підтвердженням і зупинкою процесу нових записів майже не було.
За більшого відставання — повільна мережа, навантажений фоловер — пропали б усі записи
останніх мілісекунд чи секунд, які лідер уже підтвердив.

Застосунок не має налаштування «хто лідер». Він знає всі три адреси і по черзі
під'єднується до них з `target_session_attrs=read-write`. Фоловер таке з'єднання
відхиляє, бо працює лише на читання. Після `docker kill` 106 спроб запису не знайшли
вузла, що приймає записи. Щойно `pg2` завершив `pg_promote()`, наступна спроба
під'єдналася до нього. Від `docker kill` до першого запису на `pg2` минуло 2,350 с,
найдовший проміжок без підтвердженого запису — 2,062 с. Майже весь цей час — виконання
команд failover, сам `pg_promote()` тривав 0,101 с.

Старий лідер після `docker start` відновився після аварійної зупинки і піднявся
лідером на старій лінії часу (timeline 1): у його каталозі даних немає `standby.signal`,
і про новий лідер він нічого не знає. У цей момент записи приймали два вузли: `pg1`
на timeline 1 і `pg2` на timeline 2. Пробний запис на `pg1` пройшов і отримав
`id = 156373` — той самий, що `pg2` уже видав іншій, підтвердженій застосунком нотатці.
Наш застосунок цього разу на `pg1` не пішов, бо мав робоче з'єднання з `pg2`, але
будь-який новий клієнт, що першим знайшов би `pg1`, писав би туди. `pg_rewind`
повернув `pg1` фоловером `pg2`: знайшов точку розходження `0/14882490`, замінив
змінені після неї сторінки сторінками з `pg2`, і пробна нотатка зникла без жодного
повідомлення. Записів, які старий лідер не встиг передати, в цьому досліді не було.
Якби вони були, `pg_rewind` так само мовчки відкинув би їх.

У нашій конфігурації ніщо не заважає двом вузлам одночасно вважати себе лідером.
Failover ручний, немає ні механізму консенсусу, який вибирав би одного лідера,
ні fencing, який гарантовано вимикав би старого. Захист дають інструменти на кшталт
Patroni з etcd: вузол лишається лідером лише поки тримає блокування в кластері
консенсусу, а старий лідер після повернення бачить, що блокування в іншого, і стартує
фоловером. Простіший варіант — не запускати старого лідера, доки його не перевели у
фоловери через `standby.signal` і `pg_rewind`.

7. Чим закінчився кожен із трьох конфліктів в експерименті 5? Чи стали дані на обох лідерах однаковими (convergence)? Якщо один запис «переміг» — за яким правилом, і чи дізнався про це автор запису, який «програв»?

Різні заголовки однієї нотатки: кожен вузол застосував зміну, отриману від іншого,
і заголовки помінялися місцями. На `pg1` тепер заголовок, записаний на `pg2`, і навпаки.
Реплікація не зупинилася, обидва вузли записали в журнал `update_origin_differs`
рівнем `LOG`. Вузли лишилися з різними даними. Ніхто з авторів не дізнався про
конфлікт: обидва записи свого часу отримали успішне підтвердження.

Видалення проти зміни тексту: `pg2` отримав `DELETE` для рядка, який сам змінив,
зафіксував `delete_origin_differs` і видалив рядок. `pg1` отримав `UPDATE` для рядка,
якого вже немає, зафіксував `update_missing` і пропустив зміну. Нотатки немає на
обох вузлах, тут дані зійшлися. Але зміну тексту втрачено без повідомлення автору —
лише рядком у журналі сервера.

Нові нотатки з однаковими послідовностями: обидва лідери видали `id` від 4005 до 4024
різним нотаткам. Після відновлення зв'язку кожен вузол отримав рядок із `id`, що вже
існує, і реплікація зупинилася з помилкою `insert_exists`. Apply worker перезапускався
кожні кілька секунд і щоразу падав на тому самому рядку: 31 спроба за хвилину
спостереження. Усі
зміни, що йшли в журналі після цього рядка, на інший вузол не потрапили б. Після
ручного пропуску змін реплікація відновилася, але 20 `id` на двох вузлах так і
позначають різні нотатки. Із непарними й парними `id` усі 40 нових нотаток без
конфліктів з'явилися на обох вузлах.

Отже, повної convergence немає в жодному досліді: у варіанті з однаковими `id` вузли
розходяться в 21 нотатці, у варіанті з непарними й парними — в одній, через заголовок.
Вбудована логічна реплікація PostgreSQL не вибирає переможця за часом: вона завжди
застосовує зміну, яка прийшла з іншого вузла. Для заголовка це дає
обмін значеннями, а не last write wins. Видалення «перемагає» зміну тексту лише тому,
що змінювати вже нічого. Про конфлікти знає тільки адміністратор — із журналу сервера
і `pg_stat_subscription_stats`. Автор, чиї дані втрачено, нічого не отримує.

8. Яку стратегію розв'язання конфліктів ви обрали б для сервісу нотаток: уникати конфліктів, last write wins, зберігати обидві версії, зливати автоматично? Як зробити, щоб два лідери ніколи не видали новим нотаткам однаковий ідентифікатор?

Основна стратегія — уникати конфліктів. Нотатка належить одному автору, тому всі записи
автора можна направляти на один «домашній» лідер, наприклад за `author_id`. Тоді дві
паралельні зміни однієї нотатки можливі лише під час розриву або переключення
домашнього лідера, а не в звичайній роботі.

Для конфліктів, які все ж трапляються, я зберігав би обидві версії, а не last write
wins. Нотатка — це текст, який користувач писав сам, і мовчки викинути одну з двох
версій означає втратити його роботу, як у нашому досліді з текстом видаленої нотатки.
Кожна зміна має нести номер версії. Якщо дві версії розійшлися, сервіс показує
користувачеві обидві й дає вибрати або зливає їх, а для незалежних полів — заголовок
на одному вузлі і текст на іншому — зливає автоматично. Видалення варто робити
позначкою з версією, а не фізичним `DELETE`. Тоді конфлікт «видалення проти зміни»
видно, і сервіс може запитати автора, чи справді видаляти змінену нотатку.

Щоб два лідери ніколи не видали однаковий `id`, діапазони мають не перетинатися
за побудовою. Так зроблено в нашому досліді: обидві послідовності мають крок 2,
`pg1` починає з непарного числа, `pg2` — з парного, і жодного конфлікту ключа не було.
Для N вузлів — крок N і різні початкові зсуви. Інші варіанти — складений ключ
`(вузол, локальний номер)` або ідентифікатори, які генерує сам застосунок
без координації: UUIDv7, ULID чи Snowflake-подібні з номером вузла.

9. Спираючись на свої результати: у якій ситуації сервісу нотаток вистачить конфігурації A, а в якій справді потрібна B? Чого не гарантує кожна з ваших конфігурацій?

Конфігурації A вистачить, коли сервіс працює в одному регіоні і всі користувачі
можуть писати в один лідер: затримка запису там кілька мілісекунд, а читання
розподіляються між фоловерами. Відмова лідера коштувала нам 2 с без записів і
жодного втраченого запису, а розриви з фоловером до 15 хвилин закінчувалися
автоматичним наздоганянням за секунди. Конфігурація B справді потрібна, коли
записи мають прийматися в кількох місцях одночасно і незалежно: сервери в різних
регіонах, де запис до віддаленого лідера був би надто повільним, або вимога
приймати записи з обох боків під час розриву мережі між дата-центрами. Тоді B
дає доступність записів, але конфлікти доводиться розв'язувати самому сервісу.

Конфігурація A з асинхронною реплікацією не гарантує, що фоловер покаже щойно
зроблений запис: 99,980% таких читань були застарілими, і read-after-write
доводиться робити в застосунку. Вона не гарантує збереження підтверджених записів
після відмови лідера — у нас втрат не було лише тому, що фоловер відставав на мілісекунди.
Вона не захищає від split brain: старий лідер після повернення приймав записи
поруч із новим. Синхронний режим зберігає підтверджені записи, але не гарантує
доступності: зникнення одного синхронного фоловера зупинило записи на 68 с.
Нарешті, фоловер, що відстав більше за межу журналу, не наздожене лідера сам.

Конфігурація B не гарантує збіжності даних: після розриву вузли розійшлися,
заголовки помінялися місцями. Вона не гарантує збереження змін: зміну тексту
видаленої нотатки втрачено мовчки. Вона не гарантує, що реплікація продовжиться:
конфлікт ключа зупинив її до ручного втручання. Унікальність `id` між вузлами
гарантується лише тим, як налаштовано послідовності. І вона не гарантує
читання власних записів, якщо користувач пише на один лідер, а читає з іншого.
